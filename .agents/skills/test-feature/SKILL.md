# Test Feature

## 1. Purpose

The `/test-feature` workflow coordinates the existing `test-writer` and `test-runner` agents to test a requested feature from beginning to end through an evidence-based, report-driven process.

The user can invoke this skill with a feature description, a specification path, or both:

```text
/test-feature Add monthly expense reports with category-wise charts and date filters.
/test-feature .agents/Specs/user-registration.md
/test-feature Implemented monthly reports; specification: specs/monthly-expense-reports.md
```

The workflow executes these stages sequentially:

1. Understand the requested feature and extract acceptance criteria from any provided specification.
2. Invoke the **Test Writer** agent (`test-writer`).
3. Require the Test Writer to create or update test files and generate a structured test plan report.
4. Execute the **Report Validation Gate** to ensure the test plan exists and is complete.
5. Invoke the **Test Runner** agent (`test-runner`) with the exact report path and feature context.
6. Require the Test Runner to execute tests per the report, diagnose failures, and document actual results.
7. Produce a consolidated final summary.

The Test Runner must strictly execute against the report generated by the Test Writer and never replace it with an unrelated test plan.

---

## 2. Required Existing Agents

This workflow integrates two specialized agents residing in the workspace:

- **Test Writer:** `@.agents/agents/test-writer/agent.md`
- **Test Runner:** `@.agents/agents/test-runner/agent.md`

Their responsibilities remain strictly separated:

### Test Writer
- Analyzes feature requirements and specification documents.
- Inspects application source code (`@app.py`, `@database/db.py`, etc.).
- Identifies happy paths, negative paths, boundary conditions, authorization boundaries, and regressions.
- Creates or updates automated tests in `@tests/` adhering to existing project conventions (`pytest`, `client` fixture).
- Generates a structured test plan report at `@.agents/reports/test-feature/<feature-slug>-test-plan.md`.
- Does not run test suites beyond what is needed to verify test creation syntax.

### Test Runner
- Reads the exact test plan report generated by the Test Writer.
- Executes the tests specified in that report using the project environment (`./venv/bin/pytest`).
- Captures exact test outcomes (passed, failed, errored, skipped).
- Diagnoses failures and classifies root causes (application defect, test defect, environment, database isolation, flaky).
- Generates an execution report at `@.agents/reports/test-feature/<feature-slug>-test-results.md`.
- Does not modify application code to force passing results.

---

## 3. Agent Invocation and Delegation

The workflow coordinates agents using the platform's supported subagent invocation mechanism (`invoke_subagent`):

1. **Invoke Test Writer First:** Launch `test-writer` with the feature request, specification path, and reporting requirements.
2. **Await Completion:** Wait for the Test Writer task to complete before advancing.
3. **Capture Report Path:** Obtain the exact file path of the generated test plan report.
4. **Validate Gate:** Verify the report exists, is readable, and satisfies all schema requirements.
5. **Invoke Test Runner Second:** Launch `test-runner`, passing the validated test plan report path, original feature context, and execution constraints.
6. **Await Execution:** Wait for the Test Runner to complete execution and failure diagnosis.
7. **Consolidate Reports:** Compile findings from both agents and link their saved markdown reports.

*Fallback:* If programmatic subagent invocation is unavailable in the execution environment, execute each agent's documented workflow sequentially without skipping steps or fabricating delegation.

---

## 4. Input Handling

Accept:
- A natural-language feature description.
- A path to an existing feature specification (e.g., in `@specs/` or `@.agents/Specs/`).
- Both a description and a specification path.

If no input is provided, ask the user what feature they want tested before proceeding.

### When a specification path is supplied:
1. Verify the file exists and is readable.
2. Read the entire specification before invoking agents.
3. Extract functional requirements, acceptance criteria, database constraints, and edge cases.
4. Pass the specification path and extracted criteria to both agents.

### When only a feature description is supplied:
Instruct the Test Writer to inspect the codebase (`@app.py`, `@templates/`, `@database/db.py`), infer expected behaviors based on established patterns, explicitly label assumptions, and ask for clarification if critical requirements are ambiguous.

> **Constraint:** Do not implement features or alter core application logic during this workflow. This workflow tests features; it does not build them.

---

## 5. Stage One: Test Writer Execution

Invoke `test-writer` with a structured prompt containing:
- The user's feature request.
- The path to any supplied specification.
- Verified acceptance criteria.
- Target application files inspected.
- The requirement to create/update tests under `@tests/`.
- The required test plan destination.

### Required Test Plan Report Destination
Save the test plan at:
```text
.agents/reports/test-feature/<feature-slug>-test-plan.md
```
*(Use a lowercase, filesystem-safe slug derived from the feature name. If a file with this name already exists, append a unique numeric suffix to preserve past reports).*

### Test Plan Report Contents
The report generated by the Test Writer must include:
1. Feature title and original user request.
2. Specification file path (if provided).
3. Relevant acceptance criteria and user stories.
4. Application files inspected (e.g., `@app.py`, `@database/db.py`).
5. Test files created or updated (e.g., `@tests/test_feature.py`).
6. Testing framework and configuration used (`pytest`, `@pytest.ini`).
7. Test scenarios covered (happy paths, negative inputs, boundary conditions, authorization, data isolation, regression).
8. Exact test function identifiers (e.g., `test_monthly_report_filter_by_date`).
9. Proposed test execution commands (e.g., `./venv/bin/pytest tests/test_feature.py`).
10. Required fixtures, temporary database isolation, and test helpers.
11. Database and safety requirements.
12. Assumptions, known limitations, and unverified scenarios.
13. Concise handoff summary for the Test Runner.

The Test Writer must return the exact absolute or relative path to the generated report upon completion.

---

## 6. Report Validation Gate

Before invoking the Test Runner, validate the handoff contract:

1. Confirm the Test Writer task completed successfully.
2. Confirm the test plan report file exists at the specified path and is non-empty.
3. Verify that the report lists the target feature, test files, test scenarios, and specific test commands.
4. Verify that the proposed test files exist in the repository.
5. Verify that database safety prerequisites (e.g., temporary database isolation) are documented.
6. Check for flagged blockers or unresolved specification gaps.

**Failure Action:** If the report is missing, unreadable, or deficient, do not invoke the Test Runner. Request correction from the Test Writer or report the blocker directly to the user.

---

## 7. Stage Two: Test Runner Execution

Invoke `test-runner` with:
- The user's original feature request.
- The verified Test Writer report path (`.agents/reports/test-feature/<feature-slug>-test-plan.md`).
- Specification path (if applicable).
- Strict execution constraints:
  - Read the test plan before executing tests.
  - Follow the proposed scenarios and commands.
  - Verify commands against project environment (`./venv/bin/pytest`).
  - Do not modify application code.
  - Do not delete or mutate real user data.

### Execution Protocol
1. **Targeted Run:** Execute the narrowest relevant test suite first (e.g., `./venv/bin/pytest tests/test_feature.py`).
2. **Broader Run:** Execute the full test suite (`./venv/bin/pytest`) when practical to check for regressions.
3. **Capture Telemetry:** Record exit codes, exact counts (passed, failed, skipped, error), and full tracebacks.
4. **Diagnose Failures:** Classify any failure as:
   - *Application defect*
   - *Test defect*
   - *Environment issue*
   - *Database issue*
   - *External dependency failure*
   - *Flaky test*
5. **No Blind Command Execution:** If a proposed command is unsafe or invalid, use a verified safe equivalent, document the deviation, and explain why.
6. **No Alterations:** Never remove failing tests, weaken assertions, or rewrite application code to obtain green test results.

---

## 8. Test and Database Safety

Both agents and the coordinating workflow must adhere to Spendly safety standards:

- Check `git status` before and after operations; preserve uncommitted user changes.
- Never run tests against production databases or services.
- Never modify, truncate, delete, or seed real user data in `@spendly.db`.
- Ensure all tests run against isolated temporary databases (`tempfile.mkstemp` via the `client` fixture).
- Never expose passwords, hashes, session tokens, or credentials in reports.
- Do not install unauthorized Python packages or alter dependency locks.
- Do not commit, push, rebase, or reset Git branches.

---

## 9. Execution Report

After test execution, the Test Runner must write its findings to:
```text
.agents/reports/test-feature/<feature-slug>-test-results.md
```
*(Use the same `<feature-slug>` as the test plan. If the file exists, append a unique suffix).*

### Execution Report Contents
1. Feature name and reference to the Test Writer test plan report.
2. CLI commands actually executed.
3. Verified test counts: Passed, Failed, Errored, Skipped.
4. Status of each individual test scenario / function.
5. Error messages, assertions, and stack traces for any failing test.
6. Root cause analysis supported by trace evidence.
7. Documented deviations from the original test plan (with rationale).
8. Unexecuted tests and the reason for skipping.
9. Verification beyond tests (import checks, linting, etc.).
10. Files modified during execution (must be none by default).
11. Remaining risks and recommended fixes.

---

## 10. Final Consolidated Response

When both stages conclude, present the consolidated results to the user formatted as follows:

### Feature
- **Feature:** Description and/or link to specification document.

### Test Writer
- **Status:** Completed / Blocked
- **Test Files Created/Updated:** Exact `@filename` paths.
- **Scenarios Planned:** Total count and breakdown (happy path, validation, boundary, auth, regression).
- **Test Plan Report:** Link or exact path to `@.agents/reports/test-feature/<feature-slug>-test-plan.md`.

### Test Runner
- **Status:** Completed / Blocked
- **Commands Executed:** Exact command(s) run.
- **Results:** X passed, Y failed, Z skipped.
- **Failure Diagnosis:** Summary of any identified application or test defects.
- **Execution Report:** Link or exact path to `@.agents/reports/test-feature/<feature-slug>-test-results.md`.

### Overall Status
Select exactly one:
- **Passed:** All required tests executed successfully with zero failures.
- **Failed:** One or more tests failed (indicating an application or test defect).
- **Blocked:** Test execution could not proceed due to missing prerequisites or invalid test plan.
- **Partially Verified:** Some tests passed, but key scenarios remain unexecuted.
- **Report Only:** Test plan was generated, but test execution was not performed.

*(Never report "Passed" if tests were not actually executed).*

### Recommended Next Action
Provide the single smallest, concrete next step based on the verified outcome (e.g., fixing an application defect, addressing a missing requirement, or running an additional test suite).

---

## 11. Error Handling & Edge Cases

- **Test Writer Fails or Aborts:** Halt the workflow immediately. Do not invoke the Test Runner. Preserve partial outputs and report the blocker.
- **Report Missing or Incomplete:** Do not proceed to stage two. Request revision or document the failure.
- **Test Runner Fails to Launch:** Report the environment limitation. Do not invent or estimate test results.
- **Tests Fail:** Record full diagnostic output. Do not attempt an automatic code fix unless explicitly directed by the user in a follow-up request.
- **No Tests Found:** Instruct the Test Writer to create the missing test suite.
